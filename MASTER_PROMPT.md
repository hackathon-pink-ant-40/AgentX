 # TestAgent AI — GitHub Copilot Master Build Specification

## Role and objective
Act as a senior full-stack engineer, quality engineering architect and hands-on coding agent. Build a functioning local web application named **TestAgent AI**, a system-agnostic synthetic data and REST API test orchestration platform. The demonstration use case is Customer Master Data Management (MDM), with Customer and Address entities, but no core engine may be hard-coded to Informatica or to those entities. The prototype must run without any external credentials or paid runtime AI API. Implement actual code, persistence, API calls, and tests, not a static UI or fabricated analytics. Use the phased execution plan below. Inspect the repository before changing files; preserve existing work. After each phase run the relevant tests and update a progress checklist. Do not claim a test has passed unless it was executed successfully. Explain any blocked feature.

## Technical baseline
- Node.js LTS supported by selected packages; React + TypeScript + Vite, Tailwind CSS, Express + TypeScript, SQLite (use a compatible driver), Faker.js, Ajv, Axios or native fetch, Mermaid.js, Recharts, Pino, Vitest and Supertest. Use npm workspaces with root scripts. Avoid unnecessary infrastructure.
- Suggested layout: `apps/web`, `apps/api`, `packages/shared`, `samples`, `storage/datasets`, `storage/logs`, `docs`, `.github`. Use shared types and versioned contracts. SQLite database under `storage/` with migrations, foreign keys and indexes. Store paths relative to an app-controlled directory, not user-provided file paths.
- Provide `npm install`, `npm run dev`, `npm run build`, `npm test`, `npm run demo:reset`. Pin compatible dependencies via lockfile, include `.env.example`, and write a README with Windows-friendly startup instructions. Use separate frontend/backend ports and a Vite proxy. Run a bundled mock target service or mount a clearly separate mock API route. All screens must use real backend endpoints; no hardcoded dashboard values.
- Create `.github/copilot-instructions.md` with durable project conventions, `docs/architecture.md`, `docs/implementation-plan.md` with checklist, and demo instructions. Do not install unapproved infrastructure or commit secrets, datasets, database, or logs.

## Navigation and UX
Enterprise dashboard with left sidebar: Dashboard, Connections, Data Models, Synthetic Data, Test Configuration, Test Execution, Audit Explorer, Release Policies. Clean, responsive layout. All buttons work; display loading, empty, error and validation states. Use a wizard: model import -> field rules -> preview -> dataset -> connection/test suite -> run -> dashboard. Include a `Load demo configuration` action that creates sample model, rules, connection, test suite, and policy idempotently, without faking test results. Provide explicit run/reset controls. Add a prominent DEMO/SANDBOX badge and prevent production targeting.

## 1 — Connections
Create/update/list connections: name, system type, environment (DEMO/DEV/QA/UAT), base URL, auth type (none, API key, bearer token, basic), secret reference, non-secret headers, timeout, max concurrency, enabled flag. Test connection via explicitly configured harmless health path. Use environment variables for secrets; never return credentials to browser or log authorization headers. Resolve relative paths against approved base URL and prevent host escapes, redirects, unsafe protocols, cloud metadata endpoints, and unauthorized targets; default to the bundled mock loopback origin only. External QA origins must be server-side allowlisted, with host/IP checks and explicit user authorization. Prevent SSRF and do not execute arbitrary scripts or arbitrary user-provided JS. No real production endpoints or credentials in the prototype. Do not send real customer data or secrets to Copilot or any model.

## 2 — Data model ingestion and intelligence
Accept a pasted or uploaded JSON document (standard JSON Schema including supported `$defs`/local `$ref`, or canonical app model) and Mermaid `erDiagram` text. Normalize into canonical model: model id/name/version; entities; fields with name, type, format, required, nullable, length, enum, primaryKey, unique, foreignKey (target entity and field), cardinality, and generation rule suggestion. Provide sample files for both formats, document supported subset explicitly, reject unsupported constructs with clear errors; never silently infer ambiguous constraints. Do not execute Mermaid content, disable unsafe links/HTML; render sanitized ER diagram. No remote `$ref` fetching. For Mermaid, support entity blocks, attribute types, PK/FK/UK and common relationship cardinality. When FK target is ambiguous, request UI mapping confirmation; do not guess silently. Display entities, attributes and relationship graph; editable key/type/constraint mappings. Save immutable model versions. Reject duplicate fields, unresolved FK references and unsupported cyclic relationships with actionable messages. Topologically order parent entities before children. JSON Schema represents shape, not necessarily relational semantics; explicit metadata or confirmation supplies PK/FK and relationships.

Example canonical model (expand with all listed fields):
```json
{"name":"Customer Master","entities":[{"name":"Customer","fields":[{"name":"customerId","type":"string","primaryKey":true},{"name":"firstName","type":"string","required":true},{"name":"lastName","type":"string","required":true},{"name":"displayName","type":"string"},{"name":"email","type":"string","format":"email"},{"name":"status","type":"string","enum":["ACTIVE","INACTIVE","PROSPECT"]}]},{"name":"Address","fields":[{"name":"addressId","type":"string","primaryKey":true},{"name":"customerId","type":"string","foreignKey":{"entity":"Customer","field":"customerId"}},{"name":"street","type":"string"},{"name":"postalCode","type":"string"},{"name":"country","type":"string"}]}]}
```

Implement deterministic semantic inference with an extensible `RuleSuggestionProvider` interface. Examples: firstName -> localized first name; DOB -> date range; email -> reserved example-domain email; status -> LOV; PK -> unique sequence; FK -> parent lookup. Confidence and rationale shown, user can edit/confirm. Optional LLM provider is a future adapter and must never be required for baseline. Copilot is the development assistant, not automatically an available runtime inference API.

## 3 — Synthetic Data Factory
Attribute rule editor with: fixed value, sequence/prefix, UUID, localized person/company/address, enum with optional weights, string length/regex (supported subset, validated), integer/decimal ranges, date/date-time/age ranges, null probability, unique values, derived fields (safe declarative concatenation), FK lookup and parent/child cardinality. Support record count per entity, dataset name, locale, seed and a fixed reference date for reproducibility; show preview of 10 records. Add country-aware names/addresses (NL, EN, DE as baseline); country/postal code consistency via configured rules. Country codes and localization are distinct. Use safe synthetic domains such as example.test, never actual contact details; use approved test identifier fixtures for national IDs, and invalid placeholders for negative tests. A Dutch BSN is nine digits; ten-digit values can be configured as deliberate invalid test cases. Do not claim Faker data corresponds to real deliverable addresses.

Data profile: valid, negative, edge, duplicate-match and orphan-FK scenarios. Negative mutation rules: missing required, null/blank, invalid length/type/enum/date/format, duplicate identity, invalid FK, boundary values, Unicode. Preserve all non-targeted constraints where feasible. Each synthetic record or test input carries scenario id, expected validity, reason, source record id and parent linkage. Keep scenarios/metadata separate from business payload. Distinguish duplicate business identity from duplicate PK. Store intentionally invalid business FK values as JSON payload fields, not as database FKs enforcing that invalid data. Validate baseline records; negative records expected to violate only intended constraints. Validate counts/weights/ranges/uniqueness feasibility and enforce a generation cap (e.g. 10,000 records) for local demo. Never loop indefinitely. Use deterministic seed and ordered generation; persist actual generated records for repeatability.

On generation, persist dataset, model version, rule snapshot, seed, reference date, timestamps, per-entity counts, scenario counts and synthetic record rows in SQLite. Export one JSON file per entity, combined JSON and optional CSV per entity under `storage/datasets/<dataset-id>/`, plus manifest. Write to staging directory, publish with rename after files are complete; use DB transaction and explicit READY/FAILED status, cleanup or recover orphan exports on failure. Only READY datasets can execute. Expose download and paginated search; do not leak arbitrary local file paths. Support preview without persistence. No need for a separate database server: dataset and result tables are logically separate within SQLite.

## 4 — Test configuration
Test suite and case editor with immutable version snapshots when execution begins. Fields: suite name, case name, operation (INSERT, UPDATE, MERGE, DELETE, READ, VALIDATE, custom), target entity, scenario selector, priority/critical flag, connection/environment, HTTP method, relative path, path/query parameters, request JSON template or field mapping, expected HTTP status list, optional response JSON Schema, declarative JSON-path assertions (equals, exists, notExists, contains, type, count, compare to input), expected outcome (positive/negative), prerequisites, ordered steps, response variable extraction (e.g. assigned customer ID), PBI/work-item reference, timeout. Use explicit safe token interpolation preserving JSON types, e.g. `{{record.customerId}}`, `{{record.firstName}}`, `{{steps.create.customerId}}`; no eval, JS or shell. Validate unresolved placeholders before sending. Input sample JSON and optional schema help payload mapping; output sample JSON can suggest schema only after user confirmation. Expected values must be explicit; do not infer every failure from response wording. Allow manual configuration of any REST JSON API, optionally add OpenAPI import as stretch only. Provide example test cases with nested mappings and separate Customer/Address endpoints. Tests must allow POST, PUT, PATCH, GET and DELETE.

## 5 — Execution engine
Select a READY dataset, suite and connection, start async in-process job, return run ID immediately; persist run status QUEUED/RUNNING/COMPLETED/CANCELLED/ERROR and counters. Use polling for live progress; server-side execution only, bounded concurrency (default sequential, maximum 5), configurable timeout and cancellation, recover interrupted RUNNING jobs as ERROR on restart. No automatic retry of mutating HTTP requests, unless an explicit idempotency contract exists. Order dependencies: insert Customer before Address, update existing customer, merge two seeded identities, read back state, optionally delete only sandbox records created by current run. Keep server-generated identifiers in execution context, never assume input ID equals target ID. Unique run namespace prevents test collisions. If a dependency fails, mark dependent tests BLOCKED with reason, not PASS. Avoid parallelizing conflicting operations. For each logical test instance create a result per test case/record or scenario pair; multi-step cases have multiple request attempts but count as one test in KPI. Store run configuration snapshot, dataset ID, model/suite/policy version, execution times, input record IDs, PBI link, each step's redacted request method/URL/body, response status/body, latency, assertion outcomes, error and correlation ID. Limit payload sizes and flag truncation. Persist results as work progresses; no dashboard reliance on parsing logs. Allow cancellation between steps and prevent duplicate finalization.

Verdict logic: PASS only if actual HTTP status is explicitly expected, response schema and all assertions pass, and required steps complete. An expected 400/422 for invalid data is a successful negative test. Unexpected 2xx is FAIL when rejection expected. Unexpected 4xx/5xx is FAIL when a response was received; transport errors/timeouts/config errors are ERROR; prerequisite failure BLOCKED; user-aborted/unstarted cases CANCELLED. Business error in HTTP 200 can fail via configurable assertion. For merge and persistence, assert via subsequent GET that state was actually changed, not merely that POST returned 200. Capture exact assertion explanations. Record per-case final status once. Support deterministic calculation and no invented results.

Logging: one append-only JSON Lines log file per run at `storage/logs/<run-id>.jsonl`, containing every REST call and outcome with runId, caseId, recordId, stepId, timestamp, latency, status, correlationId and redacted request/response. All calls for a run go into this single file. Write logs and structured result records; flag logging failures. Protect secrets and redact sensitive keys/query values in both logs and database. Persist redacted evidence; if production audit requires original restricted payloads, design separate controlled storage later. Provide download of this log through a safe API.

## 6 — Bundled mock MDM target (real HTTP behavior)
Implement stateful mock REST service with isolated demo records and realistic behavior: POST /customers (201, validate required and duplicate ID); GET /customers/:id (200/404); PATCH /customers/:id (200/404/422); POST /customers/merge (200, retain survivor, reparent addresses, remove/mark merged record); POST /addresses (201, 422 for unknown customer); GET /customers/:id/addresses; DELETE /customers/:id (explicit semantics, sandbox only). Return documented JSON errors. Add a visible `simulate regression` toggle: e.g. invalid payload unexpectedly accepted, or merge fails to reparent address. Baseline mode passes all configured cases; regression mode produces actual failed assertion(s) and quality gate NO-GO. No mock result fabrication. Include demo cases covering insert, update, read-back, merge with state validation, duplicate ID rejection, missing required rejection, orphan address rejection, Unicode round-trip. Seed prerequisites in test steps; do not use manual setup hidden from audit. Include repeatable demo reset and a unique namespace for reruns.

## 7 — Dashboard and audit explorer
Run selector and filters by entity, operation, case, status, PBI, dataset, environment and date. Display planned, executed, passed, failed, errors, blocked, cancelled, pass rate, coverage, elapsed time and critical failures. Charts: status donut, stacked bar by entity, stacked bar by operation, historical pass-rate trend; filters recalculate metrics from stored results. Click chart/row to drill down to case and evidence. Audit Explorer tabs: synthetic records and test results; paginated searchable list by record ID, customer ID, entity, case, run and PBI. Detail includes source synthetic record, input payload, output payload, expected versus actual HTTP status, assertions, timestamps, duration, scenario and correlation ID. Link to dataset export and run log. Data survives server restart. Include loading/empty/error states. Do not claim full RBAC in hackathon; treat as local single-user with future auth/RBAC boundary.

## 8 — Quality gates and defect workflow
Release policy: pass threshold (default 80%, editable), minimum coverage (default 100%), max critical failures (default 0), allowErrors/allowBlocked (default false), scope environment, policy version. Planned count = logical test instances; executed count = PASS+FAIL+ERROR; pass rate = PASS/planned *100; coverage = executed/planned *100. Report conventional executed-only pass rate separately if desired, but use conservative planned denominator for gate. No tests, incomplete/cancelled run, any critical non-PASS, below threshold, below minimum coverage, or disallowed ERROR/BLOCKED -> NO-GO. Compare unrounded values. Only evaluate final run; running state PENDING. Record policy snapshot, decision and explicit reasons. Provide a promotion recommendation, never actual deployment, production auto-promotion or authorization bypass. Enterprise CI/CD integration should honor approvals and change controls.

On NO-GO, group failed tests by stable signature (case, endpoint, assertion/error, environment); create local defect candidates with title, severity, linked PBI, steps to reproduce, expected vs actual, run link, record IDs, redacted evidence and occurrence count. Keep historical observations, deduplicate within run and across runs for same unresolved defect. Export JSON for future Azure DevOps PBI creation. Design `WorkItemProvider` interface with mock/local implementation; future approved Azure DevOps/Jira connector. No external ticket creation by default. Distinguish failed assertions from infrastructure errors and blocked dependencies.

## 9 — Sprint automation (stretch)

Input: sprint ID, linked work items, dataset profile, suite ID, connection ID, policy ID. Fetch approved test mappings, generate data, run suite, evaluate gate, create local defects, return decision. Missing test mappings must be surfaced as gaps, not ignored. Future provider can import acceptance criteria and suggest versioned test cases; human approval required before execution of new mutating tests. Future webhooks authenticated, authorized, replay-protected and integrated with pipeline approvals. For hackathon, simulate event locally and do not connect real corporate boards or deploy anything. Keep core APIs compatible with a later headless CI job.

## Build phases — complete vertically, do not attempt all UI at once
1. Foundation: repo scaffold, SQLite migrations, shared types, mock target, basic UI navigation, smoke test. Demonstrate app starts and mock HTTP endpoint responds.
2. Model + data: JSON canonical/Schema import, Mermaid subset import, review/mapping, generator, preview, DB and exports. Demonstrate 20 customers and related addresses, reproducible seed, deliberate invalid records and data search.
3. Execution vertical slice: connection, case editor, request mapper, HTTP executor, expected status/assertions, multi-step dependencies, persistence, single JSONL log. Demonstrate insert, update, negative rejection and merge/GET verification against mock target.
4. Analytics + gate: real run metrics, run selection, audit drill-down, configurable gate, local defect candidates/export, regression toggle. Demonstrate healthy GO and regression NO-GO. This is hackathon definition of done.
5. Stretch only after green tests: sprint-close demo event, OpenAPI import, optional AI suggestion adapter, CI/CD and work item provider interfaces. Do not sacrifice working stages for stretch.

## Acceptance tests
- Clean install/build/start; no external credentials. App and mock run locally; all core UI routes work.
- Import both sample formats; ambiguous FK asks user to map; invalid schema is rejected clearly. Version snapshots remain stable after edits.
- Generate at least 20 customers and 1–2 addresses each. Positive records maintain FK linkage, generated IDs unique, derived display names correct, same seed/rules/reference date reproduce same records, intentional orphan fixture is retained and marked.
- Export manifest and datasets, search DB records after restart, no partially created dataset treated as READY.
- Run positive insert/update/merge/read-back and negative tests through actual HTTP requests. Expected 422 passes; unexpected 200 on negative fails; HTTP 200 with wrong business data fails; timeout -> ERROR; failed prerequisite -> BLOCKED. Multi-step test counts once. All calls appear in the one run log; secret headers absent.
- Dashboard counts equal persisted result records; entity filters and drill-down work; history survives restart.
- Gate passes a baseline run, fails simulated regression (critical test or threshold), fails empty/incomplete run; defect candidates deduplicated and exportable. No actual deployment or external work item creation.
- Tests for parser, generator, template mapper, executor verdict logic, metrics, gate, and an integration test running mock service end-to-end. Test allowed/blocked target origin and secret redaction. Print actual build/test results and document known gaps.

## Execution instruction
First inspect the workspace and write the implementation checklist. Then implement Phase 1 immediately, run it, fix errors, and proceed phase by phase if the preceding phase works. Prefer a smaller working end-to-end slice to many incomplete screens. Keep commits/changes scoped, do not overwrite unrelated files, and ask for approval before external network access beyond dependency installation or any real system action. If time is constrained, defer optional features explicitly and keep the core demo runnable. At the end provide exact startup commands, demo walkthrough, actual test/build status, known limitations, and next-phase recommendations.
